# Analytics: what is measured and where

Two sources, deliberately separate:

| Source | Answers | Where |
| --- | --- | --- |
| **Supabase** (`get_dashboard_insights`, `get_dashboard_metrics`, `get_dashboard_activity`) | *What happened to tournaments*: volume, completion, funnel, formats, feature adoption, retention. Based on real tournament data. | The `/dashboard` page (admins only). |
| **PostHog** (events below) | *What people did in the app*: setup friction, feature use, notifications, sharing. Based on behavior. | PostHog project. |

**Privacy rule for every event:** only enums, counts and booleans. Never player names, tournament names, emails, tokens or free text.

## Dashboard (Supabase)

| Tab | Content |
| --- | --- |
| Resumo | KPI cards with change vs the previous period and sparklines; plain-language insights; daily trend; funnel (iniciaram → 1º placar → metade → rodadas → finais → finalizaram). |
| Uso e recursos | Mix of format/size/doubles/hosting; completion by format; start-time heatmap (day × hour, in the viewer's time zone); feature adoption; moderator retention; shared-tournament registration funnel. |
| Torneios | Live and archived tournament lists, where tournaments stopped, raw counters. |

Notes for reading the numbers:
- **Periods** are the last 7/30/90 *local calendar days*, today included; "previous" is the same length just before.
- **Funnel and adoption** only count tournaments with known progress (shared, or local with a full archive, or already finished). The coverage line says how many local tournaments that excludes.
- **Duration** is the median and p90 of finished tournaments (the mean was skewed by tournaments left open).
- A zero baseline shows "novo", never an invented percentage.
- The insights panel is generated by `core/dashboard-insights.ts` (`buildInsights`); each rule needs a minimum sample so small numbers do not raise alarms.

## Suggested PostHog insights

Build these once; they map to the questions the dashboard cannot answer on its own.

1. **Activation funnel:** `app_opened` → `tournament_setup_step_completed` (step 1) → `player_added` → `tournament_started`. Break down by `hosting_mode`. Where do first-timers leave setup?
2. **Completion funnel:** `tournament_started` → `match_score_recorded` → `finals_generated` → `tournament_finalized`. Compare with the dashboard funnel to separate "app friction" from "event ended".
3. **Projection adoption (shared):** unique users with `qualification_opened` ÷ guests per tournament; trend of `qualification_whatif_used` per opener (is "E se?" discovered?); `chance_notification_opened` ÷ `chance_notification_shown` (do alerts bring people back?).
4. **Confirmation friction:** `tournament_finalize_cancelled` ÷ (`tournament_finalized` + `tournament_finalize_cancelled`). A high ratio means the typed confirmation is too heavy or unclear.
5. **Return behavior:** weekly retention on `tournament_started`; `tournament_library_opened_item` per returning user shows whether history is used.
6. **Tutorial value:** `tutorial_finished` vs completion of `tournament_setup_step_completed` by `step`.

## Adding an event
1. Capture with `this.posthogService.posthog.capture('snake_case_name', { ...enums and counts only })`.
2. Add it to the table above in the same change.
3. If it answers a recurring product question, add it to the dashboard (Supabase) only when the data is in the database; behavior stays in PostHog.
