# CLAUDE.md

Guidance for AI agents and developers working in this repository. Keep it short; long-form decisions live in `docs/`.

## What this is

SETPOINT: a beach tennis tournament manager. Angular 20 standalone SPA (pt-BR UI), Supabase (SQL migrations, RPCs, realtime), PostHog analytics, hosted on GitHub Pages. The active work is the professionalization plan in [docs/professionalization-plan.md](docs/professionalization-plan.md); read its Engineering standards and Phase sections before changing structure.

```bash
npm run db:reset        # re-apply all migrations
npm run test:db:supabase # pgTAP security and permission tests on the real local stack
npm run db:lint         # splinter + supabase db lint (fails on any ERROR or unexpected WARN)
npm run db:migrations   # forward-only and vendor-neutral migration rules

npm run e2e:visual      # visual baselines (e2e/visual.spec.ts) in the Playwright Docker image CI uses; needs Docker
npm run e2e:visual:update # rewrite e2e/__screenshots__ (only for a change that is meant to be visual)
npm run e2e:prod         # production build, then the smoke tests (e2e/production.spec.ts) under the /setpoint-beach-tennis/ base path
npm run build           # production build (run scripts/generate-runtime-config.cjs first)
npm run analyze         # production build with stats (dist/setpoint/browser-stats.json, for esbuild's analyzer) and dist/bundle-report.html (source-map-explorer); overwrites dist/
npm run perf:lighthouse # Lighthouse CI on dist/ (advisory in CI: its own non-blocking job); build first with npm run build -- --base-href /setpoint-beach-tennis/ (Supabase mocked, see lighthouserc.cjs)
npm run check           # lint, styles, format, typecheck, knip, tests, build
```

Local runtime config is `public/runtime-config.js` (tracked, development values). Do not overwrite it. CI and deploy regenerate it with `scripts/generate-runtime-config.cjs`.

## Architecture (current)

- `src/app/app.component.ts` and `.html`: the shell (about 300 lines of logic, OnPush): lock screen, landing gating, top bar and nav, the address glue, and rendering the features. What it knows is signals; do not add new features here, put new code in the target structure. What it used to do by hand is in services: `core/sync/tournament-sync.ts` (`TournamentSync`: the offline queue, the send loop, pause, the poll; its status is signals; sync errors are typed `SyncErrorKey`s, words in `SyncErrorText`; read `pendingNow()` before throwing a queue away, `hasPending` is cached), `core/archive/tournament-archive.ts` (`TournamentArchive`: "Meus torneios", the upload and the usage metrics), `core/tournament-persistence.ts` (`TournamentPersistence.save`: what every change to the tournament calls), `core/notices.ts` (`Notices`: the one message on screen; the shell's own messages are `ShellNoticeKey`s with words in the root `shell.notice.*`), `core/routing/app-navigation.ts` (`AppNavigation`: the page and the address), `core/shell-context.ts` (`ShellContext`: whether the address is someone else's tournament) and `core/theme.ts` (`ThemeService`). `src/app/shell/` holds what orchestrates the features and may import them: `TournamentLifecycle` (draw the schedule, reset, archive a shared tournament, import a backup, open a saved tournament; confirmations in the root `shell.confirm.*`), `ShellStartup` (restore what the device holds, start the background work), `ShellState` (what the pages and the profile panel show of the sync and the theme, as computed signals), `ShellDialogs` (the lazy profile panel and "Meus torneios"), `AnalyticsIdentity`, `shell-prefetch.ts` (the tournament chunk and its text are loaded at start: scoring must work offline) and `provideHostProjection`. A feature never talks to the shell through hooks: it replaces the tournament in `CurrentTournament`, calls `TournamentPersistence.save` and `Notices.show`, and asks the shell for what only it can do through `ShellRequest`. Text the shell shows is root Transloco keys (`shell.*`); a value that reaches a template must be a signal, or the OnPush shell will not refresh. When the address opens someone else's tournament (`isSharedView`: `?live=`, `?invite=`, `?dashboardTournament=`), it renders only the shell and the lazy shared view, and none of the owner startup (device tournament, sync queue, library, version reset) runs. `OwnedSharedTournament.applied$` and `LocalLiveLink.published$` are events the services above react to, so the lower layers never call up (a subscriber's error does not reach the emitter: catch inside it).
- `src/app/core/ports/`: vendor-neutral interfaces written in the app's terms, each with an `InjectionToken` (`AnalyticsPort`, `ErrorReporter`, `SurveyPort`, `AuthPort`, `SharedTournamentRepository`, `LocalLiveRepository`, `TournamentFeed`, `ArchiveRepository`, `DashboardRepository`, and the browser group `KeyValueStore` (`LOCAL_STORE`, `SESSION_STORE`), `Clock`, `Random`, `AppConfig`, `Connectivity`). Features and AppComponent inject ports only. `ports/testing/` holds in-memory fakes and the contract suites that both the fake and the real adapter pass (`SHARED_TOURNAMENTS`, `LOCAL_LIVE` and `DASHBOARD` fakes cover the guest and viewer reads; `FakeTournamentFeed.watching()` shows open watches).
- `src/app/core/adapters/<vendor>/`: the only place that imports `@supabase/*` or `posthog-js`, and `core/adapters/browser/` is the only place that touches `localStorage`, `sessionStorage`, the real time (`Date.now()`, `new Date()`), `Math.random`/`crypto` or `window.__SETPOINT_CONFIG__` (ESLint enforces both; specs are exempt). Inject `LOCAL_STORE`, `SESSION_STORE`, `CLOCK`, `RANDOM` and `APP_CONFIG` instead. The three schedule files keep a `Math.random` default on a documented ESLint exemption until they move into `domain/`. `src/app/app.config.ts` is the composition root that binds ports to adapters; swapping a vendor is a new adapter folder plus one line there. See ADR 0003 and `docs/vendors.md`. Adapter specs use a fake client (`fake-supabase-client.ts`) or an injected SDK; the Angular unit-test builder does not support `vi.mock` on relative imports, so inject what you need to fake.
- `src/app/domain/`: framework-free logic over the app's models, pure functions with no Angular, RxJS, vendor, `ui/` or feature imports (ESLint enforces it; from `core/` only types). `domain/tournament-setup/` holds the setup rules (the sizes, courts and rounds a format allows, the transitions between choices, the player and batch checks) as functions that return a new tournament or an error as data; the wizard and the Ajustes page both use them. `domain/tournament-view/` derives what screens show from a `TournamentState`: standings (`createStandingsMemo`), group tables, progress and elapsed time, viewer rounds, a player's matches, the qualification rule and `normalizeSharedState`. It returns data, not text: the caller formats and translates. `bracket.ts` (`finalsBracket`) turns the finals into the knockout tree (columns of cells, seeds, feeds, synthesized bye nodes) for the 20-athlete bye format and the mixed 8-pair knockout, and returns null for Super and mixed direct; the layout is found by match id, the contract `FinalsService.updatePodium` uses. A rule that needs a vendor is passed in (finals take `FinalWinnerSide`, today `FinalsService.winnerSide`). Specs build states with `src/app/testing/tournament-state.ts`.
- `src/app/core/`: the remaining domain logic and services (`storage.service.ts`, `state-machines.ts`, `offline-sync-queue.ts`, `scenario-engine.ts`, ...). Unit tests are colocated `*.spec.ts` files run by Vitest.
- `src/app/features/`: `features/README.md` is the pattern every extracted feature follows (folder layout, component-scoped signal store, sources on ports, `@defer` from `AppComponent` until the router is the default, Transloco scope, fakes and tests). `shared-view/` is the reference (live link, invite, admin viewer); `dashboard/` (`/dashboard`: the e-mail sign-in and the admin numbers) follows it and reacts to `AUTH.onAuthStateChange` itself. `landing/` (the first-visit page) is the first feature with its own stylesheet: its rules left `styles.css` for `landing.component.css`. `setup/` (the setup wizard: the page frame plus three step bodies as children, the tour, and the batch players dialog) is the first page of several steps; its state sits in root services (`CurrentTournament`, `OwnedSharedTournament`, `SetupProgress`, see `features/README.md`). `profile/` (the profile panel) and `library/` ("Meus torneios") are the first features that are dialogs: `AppComponent` opens them lazily through `DialogService.open` (the profile as a popover under the top bar, `anchor`), they own their content and CSS, and the shell keeps the gating (`welcomeThen`, `profileOpen`). What the shell and the dialogs share about the device lives in two root services in `core/`: `LocalProfileStore` (the saved profile, as signals) and `SavedTournaments` (the one `TournamentLibrary` over `LOCAL_STORE`, plus the list the screens show). `tournament/` holds the organizer's six pages and what several features share. `app-tournament` (`display: contents`, provides `TournamentStore` and the `organizer` and `tournament` Transloco scopes) renders the page the shell asks for (`page` input) as a `<section>` child (`appOverviewPage`, `appPlayersPage`, `appRoundsPage`, `appRankingPage`, `appProjectionPage`, `appSettingsPage`), so moving between pages keeps the store (half-typed scores, the share pick, the clock). The shell hands it what it knows through one signal input, `shell` (`TournamentShellState`: the sync state and the theme, `ShellState.tournament`; the profile dialog reads `ShellState.profile`), and hears what only it can do as `ShellRequest` (navigate, finalized, cancel the shared tournament, reset, import a backup `File`, open the library or the landing page, pause or run the sync). Scores are never edited in place: the store replaces the tournament through the pure functions of `domain/tournament-play/` and `domain/tournament-setup/` (the Ajustes rules form) and asks the shell to save (`CurrentTournament.save`); what a person typed that is not a score yet is a draft in the store. The cards of Ajustes that carry their own actions are `article` children (`appLiveLinkCard`, `appSyncCard`, `appDataCard`); the public live link is the root service `core/local-live-link.ts` (`LocalLiveLink`: tokens in `LOCAL_STORE` under `setpoint.local.live.<analyticsId>`, the shell's sync reads `writeToken()`). The tie draw is a `DialogService` dialog (`tie-draw-dialog/`), and no hand-rolled modal is left. The model-aware flat components live in `components/` (`ranking-view`, `podium`, `final-live-score`, `round-navigation`, `match-score-form`, `tournament-report`, `battle-card`, `qualification-stats`); the shell-only questions a page asks (navigate, the tournament was finished) leave the store as `ShellRequest`. Shared with the guest views: the player-matches and share-results dialogs and the projection (`ProjectionController`, provided per page, and `ProjectionPanelComponent`, used by the host's Projeção page and the guest's Meu caminho). `SelectedRound` (root) is the round Partidas shows, so it outlives the page. The older presentational components are still flat in `features/`.
- `src/styles/tokens.css`: the design tokens (colors, spacing, radius, elevation, motion; light and dark). Pinned by `e2e/design-tokens.spec.ts`: change a value there in the same commit. `src/styles/components/{button,card,dialog}.css` style the `ui/` components. `src/styles.css` is the remaining global stylesheet (still being split, Phase 5); read colors from tokens, never hard-code a text color (light-theme AA needs `--muted`, `--accent-text`, `--success-text`). `tokens.css` is the only place for a colour literal: a hex, `rgb()` or named colour in any other rule is a Stylelint error (`declaration-property-value-disallowed-list` and `color-named`; custom properties are free). Palette primitives (`--white`, `--ink-*`, `--gold-*`, ...) are the same in both themes; a value that differs by theme gets a themed token (`--chip-*`). A translucent value is `rgb(from var(--base) r g b / N%)`, or a named `--<base>-<N>` token inside a gradient (a computed colour rounds alpha differently from a literal in gradients, and the baselines catch it); `color-mix()` moves pixels, so do not use it for these. A new token goes into `e2e/design-tokens.spec.ts` for both themes.
- `src/app/core/routing/`: the app's URLs. `app-url.ts` holds the URL shapes as pure functions; `UrlState` (`URL_STATE`) is what `AppComponent` and the features use instead of `window.location`, `history` or `URLSearchParams` (don't use those directly). `LegacyUrlState` is the original code and `RouterUrlState` is the Angular Router, chosen in `src/main.ts` by the `routerEnabled` flag (default off; the router is a lazy chunk). The URL shapes did not change (ADR 0005). `e2e/url-contract.spec.ts` must pass in both modes (`chromium` and `chromium-router` projects).
- `src/app/ui/`: the design system (`@ui/*` alias). `uiButton` and `uiCard` render the same `.button` and `.surface-card` classes templates still use; `ConfirmDialog` is opened through `DialogService` (core) on `@angular/cdk/dialog`. A feature's own dialog is a component opened with `DialogService.open(component, { data, labelledBy, sheetBelow })` (focus trap, Escape, click outside, focus restored); it reads `DIALOG_DATA` and closes through `DialogRef` (examples: `features/tournament/player-matches-dialog`, `share-results-dialog`). Never hand-roll a backdrop. `ui/` imports only Angular, the CDK and itself (ESLint enforces it). New features use these instead of copying markup; migrate `class="button …"` and `class="surface-card"` as each feature is extracted.
- `supabase/`: `migrations/` (forward-only), `tests/` (pgTAP), `lint/` (splinter), `config.toml` (Supabase CLI). Security findings and rules: `docs/security.md`.
- `src/app/shared/parsers/`: Valibot parsers for everything that comes from outside (RPC responses today). Do not cast RPC data with `as`; add a parser.
- `src/app/core/i18n/` sets up Transloco (ADR 0004). Text lives in `public/i18n/<scope>/pt-BR.json`, loaded at runtime; the root `public/i18n/pt-BR.json` holds the app shell (`shell.*` keys). An extracted feature provides its scope with `provideTranslocoScope` and has no raw text in its template. Specs import `translocoTesting()` from `src/app/testing/` to get the real pt-BR text. `npm run i18n:check` also runs `scripts/check-raw-text.mjs`, which fails on Portuguese text in templates and on accented string literals in non-spec code; files still to be converted are listed in its `PENDING` set, which only shrinks (a file with nothing left must be removed from it). Text read by `core/` and `ui/` uses root keys (`common.*`, `shell.*`); a key that carries user data as a parameter must not contain `{{x}}`.
- `src/index.html` holds the Content-Security-Policy. A new external host needs a CSP change and a test; fonts are self-hosted (`src/fonts/`).

Target structure, ports and adapters, and feature folders: Phase 4 and ADR 0003 in `docs/adr/`.

## Engineering rules (enforced)

- Conventional Commits. Enforced by commitlint on commits (husky hook) and on PR titles (CI).
- Never silence a gate: no `eslint-disable`, `@ts-ignore`, `stylelint-disable`, skipped tests, or baselines. Fix the code, or reduce scope and say so.
- Ratchet: rules that legacy code cannot pass are enabled only for the folders that comply (see `eslint.config.mjs`). Widen the glob as code is migrated.
- Persisted data (`setpoint.tournament.v1`, offline queue, shared snapshot) and database changes must stay backward compatible with the previous release.
- Migrations are forward-only. Never edit a migration already on `main`. New functions are private by default (`revoke` is the default privilege); grant `execute` on purpose and add the function to the allowlists in `supabase/tests/security.test.sql`. New SQL uses `app.current_user_id()`, not `auth.uid()`.
- Do not commit or push unless the user asks.
- `docs/metrics.md` is a local-only file. Never `git add` it, never include it in a commit or PR, and do not paste its numbers into committed docs as a substitute.

## Unit tests (Vitest)

Specs are `src/**/*.spec.ts`, colocated with the code, run by `ng test` (Angular unit-test builder, Vitest, jsdom). Import `describe`, `it` and `expect` from `vitest` (no globals). Import the real modules and build services and components through `TestBed` (`TestBed.inject`, `runInInjectionContext`); never stub `@angular/core`. `src/app/testing/` holds shared test helpers. Property tests use `fast-check` in `*.property.spec.ts` next to the module (schedule shuffle, scenario engine, qualification); failures print a seed, so rerun with `fc.assert(..., { seed, path })` to reproduce. Use `seededRandom` for the code's own random source. The SQL tests in `tests/` stay on `node:test` (`npm run test:db`).

Coverage thresholds live in `angular.json` (`test.options.coverageThresholds`) and measure `src/app/core/` and `src/app/domain/`; CI runs them through `npm run test:coverage`. They are a ratchet: raise them when coverage rises, never lower them. Measured on 2026-11-16 after the setup extraction: statements 80.31, branches 77.32, functions 88.19, lines 80.21 (the thresholds are the floors, rounded down). New code must be covered.

## End-to-end tests (e2e/)

- Playwright runs the real app. `e2e/support/fixtures.ts` blocks every host except localhost, so tests never reach Supabase, PostHog or Google Fonts, and it starts like a returning user (landing, tour and profile prompt skipped). Use its `test`, never the raw Playwright one.
- The suite runs on the dev server, because every test also fails on Angular's dev-mode warnings (NG0100, NG0955, NG0956) and the production build never raises them. `e2e/production.spec.ts` is the small smoke of the production build under the Pages base path (`npm run e2e:prod`, `E2E_PROD`, CI job `e2e-production`): base path, deep links, lazy chunks, CSP without dev mode. Its addresses are relative (`./`).
- CI splits the suite into 3 shards of 4 workers and records a trace only on a retry. A test that passes only on its retry is flaky: a pull request still passes and the `github` reporter lists it; the nightly run (schedule) runs each test 3 times and fails on any flaky test (`E2E_FAIL_ON_FLAKY`). Fix a flaky test, do not raise timeouts or retries to hide it.
- Select elements by role and accessible name. The fixture seeds `Math.random`, so the draw is the same on every run; still prefer asserting structure (counts, headings, saved state) over player names. Ties are resolved by `generateFinals`. Use `test.use({ randomSeed: null })` only to test real randomness.
- Visual baselines (`e2e/visual.spec.ts`, project `visual`, PNGs in `e2e/__screenshots__/`): landing, setup and its tour popover, rounds, ranking, finals, the share-results dialog, the final report, the podium, projection, profile panel, library and delete confirmation, live viewer, guest invite and dashboard login, on desktop in light and dark and at phone width (390 px) in light. Colour is exact (`threshold: 0`); full-page shots may differ by at most 32 pixels (raster noise at the edge of the fixed blurred bars), overlay shots by none. CI never writes a missing baseline and does not retry them. They are expected output, not a suppression baseline: a style refactor must pass them unchanged. They do not see everything (for example the dark `.qual-chip` colours and the player-matches dialog, whose inner scroll position varies by a pixel between runs, are in no shot), so a refactor also compares the built CSS. Regenerate only with `npm run e2e:visual:update`; CI runs the project in its own `visual` job inside the same Playwright image (a local Chrome or the ubuntu runner renders differently, so `npm run e2e` and the `e2e` job leave it out unless `E2E_VISUAL` is set). Only for a change that is meant to be visual, and name each changed image in the PR. If the `visual` job fails, review the diff images in its artifact first.
- Accessibility is a ratchet: `e2e/a11y-baseline.json` holds the axe violations of each screen, and today every screen is `{}` (zero): the shell, lock screen, dashboard sign-in, the dialogs (profile, library, confirm, share results, player matches, tie draw) and the main pages in light and dark. A page fails when a rule appears or grows; a new screen must be clean when it is added. Do not edit the file by hand upward (`A11Y_RECORD=1` only lowers). `e2e/a11y-navigation.spec.ts` covers what axe cannot: the skip link, the title and heading focus on a screen change (`shell/page-announcer.ts`), and reduced motion. Every field that removes the default outline must show `:focus-visible` with the global ring (`--focus`); a status colour on a tinted background needs an opaque themed chip token, because translucent tints dropped text below 4.5:1.
- Persisted-data fixtures live in `tests/fixtures/persisted/<kind>/v<N>.json` and are never edited. When a stored shape changes, add a new version and keep the old one.
